# kv-store-grpc: build and serve a stateful gRPC KV service in Python

## What every member of this family requires (invariants)

The test harness evaluates a **live gRPC endpoint**, not just source files.
Tests are pytest-run and connect over the wire in a shell that comes *after*
your session ends. Every family member therefore requires the same closure:

1. A `.proto` file you write, encoding **exactly** the RPC contract from the
   task instruction (service name, method names, message names, field names,
   field numbers, types, cardinality).
2. Python bindings generated by `grpc_tools.protoc` at the **mandated absolute
   paths** (generated names must be importable from the working directory).
3. A servicer implementation holding **in-memory state that persists across
   calls and across client channels** for the server's lifetime.
4. A real server process, **detached and left running** on the mandated port,
   that survives your shell exiting and answers correctly under repeated
   channels and concurrent bursts.

The variety comes from three dimensions (see also the task spec): (a) richer
proto contracts, (b) richer state semantics, (c) harsher runtime conditions.
The pipeline below is fixed; only the details you transcribe change.

## Step 0 — extract the contract before writing anything

From the instruction, write down (do not skip any):
- **Versions**: exact `grpcio` / `grpcio-tools` pins if given (install them
  verbatim; if none are given, install the latest of both *together*).
- **Service name**, and for each RPC: method name, request/response message
  names, and every field with `name`, `number`, `type`, `repeated`/`optional`.
- **Semantics** per RPC, including what happens for missing keys, missing
  namespaces, deletes, overwrites, resets, conditional or aggregate reads,
  multi-key operations. Tests compare against these on the wire.
- **Artifacts**: exact paths for the proto and both generated modules (seed:
  `/app/kv-store.proto` → `/app/kv_store_pb2.py`, `/app/kv_store_pb2_grpc.py`),
  the required servicer **class name** (seed: `Server`), and the **port**
  (seed: `5328`).

Field numbers and types are wire-format identifiers: the grader's client stubs
are compiled against the instruction's numbers, so a different number or type
silently garbles data. Transcribe them character-for-character.

## Step 1 — environment and dependencies (container is minimal; probe first)

Observed in the anchor environment (re-check cheaply before relying on them):
- `python3` is Python 3.13 at `/usr/local/bin/python3`; another interpreter
  (python3.11) exists but has **no** grpc packages. Always install and run with
  the same interpreter: use `python3 -m pip` everywhere, never bare `pip`.
- grpcio / grpcio-tools are **not** preinstalled; network package installs work
  and you run as root.
- There is **no** `protoc` binary. Code generation goes through
  `python3 -m grpc_tools.protoc` (provided by grpcio-tools).
- Coreutils are minimal: **no** `ps`, `pgrep`, `ss`, `netstat`, `lsof`,
  `curl`, `wget`, `nc`, `socat`. Do all diagnostics with Python (`socket`,
  `/proc` scanning) — the snippets below already assume this.

Install (matching the instruction's pins; seed values shown):
```bash
python3 -m pip install grpcio==1.73.0 grpcio-tools==1.73.0
```
Install system-wide (no venv); generated code needs only `grpcio` at runtime;
`protobuf` comes in automatically at a version compatible with the pinned
tools. Never mix: whichever `python3` installed the packages must be the one
that runs the server. If a pinned version fails to build (minimal containers
have no C compiler) it usually means no prebuilt wheel exists for this
interpreter — fall back to the newest `grpcio`/`grpcio-tools` pair that ships
a wheel; runtime compatibility matters more than the exact pin, which is only
mandatory when the instruction says so.

## Step 2 — write the proto file

Proto3 unless the instruction says otherwise. Package name is your choice (the
wire format ignores it). Skeleton:

```proto
syntax = "proto3";
package <any_name>;

service <ServiceName> {
  rpc <Method>(<RequestMsg>) returns (<ResponseMsg>);
  // ... one rpc line per method, signatures verbatim from the instruction
}

message <Msg> {
  <type> <field_name> = <field_number>;            // scalars: string, int32, int64, bool, bytes, ...
  repeated <MsgType> <field_name> = <N>;           // list-valued
  optional <type> <field_name> = <N>;              // proto3 field presence
  enum <EnumName> { <VAL_A> = 0; <VAL_B> = 1; }    // enum field must start at 0
}
// nested messages: declare message inside message to get generated nested classes
```

Rules that generalize across naming variations:
- The generated **module name** comes from the proto file's basename with
  dashes converted to underscores (`kv-store.proto` → `kv_store_pb2.py`,
  `kv_store_pb2_grpc.py`). To control the module names, control the proto
  filename so its dash-to-underscore form equals the required module stem.
- The generated Python symbol names derive deterministically: service `S` →
  class `SServicer`, class `SStub`, function `add_SServicer_to_server`.
  protoc converts declared field names to snake_case in Python and keeps
  message/enum type names as declared.
- **After generating, read or introspect the generated module** to confirm the
  exact class/field names before writing the server. Do not guess.

## Step 3 — generate the bindings (and regenerate after every proto edit)

```bash
cd /app
python3 -m grpc_tools.protoc -I/app --python_out=/app --grpc_python_out=/app /app/kv-store.proto
```
- If ANY output already exists, delete or regenerate it — stale bindings
  desynchronized from an edited proto are a classic silent failure.
- `grpc_tools.protoc` exits non-zero and prints the offending lines when the
  proto does not parse. Re-run it after **every** proto edit and require exit
  0 before moving on.
- Verify importability from the artifact directory immediately:
  `cd /app && python3 -c "import kv_store_pb2, kv_store_pb2_grpc"`.
- If the instruction mandates module names that differ from the proto basename
  (rare), rename the two generated files and fix the `import <orig>_pb2 as ...`
  line at the top of the renamed `_pb2_grpc` module.

## Step 4 — implement the server

Shape that works for every variant:

```python
import threading
from concurrent import futures
import grpc
import <mod>_pb2, <mod>_pb2_grpc

class <RequiredClassName>(<mod>_pb2_grpc.<ServiceName>Servicer):
    def __init__(self):
        self._lock = threading.Lock()
        self._state = {}          # your storage layout, e.g. {namespace: {key: value}}

    def <Method>(self, request, context):
        with self._lock:
            # read/modify self._state per the instruction's semantics
            return <mod>_pb2.<ResponseMsg>(<field>=..., <field>=...)

def serve():
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=32))
    <mod>_pb2_grpc.add_<ServiceName>Servicer_to_server(<RequiredClassName>(), server)
    server.add_insecure_port("[::]:<PORT>")   # or "0.0.0.0:<PORT>"
    server.start()
    server.wait_for_termination()

if __name__ == "__main__":
    serve()
```

Decision rules, mapped to the variation axes:

- **State semantics (axis 2).** One servicer instance registered once ⇒ state
  lives as long as the process and is shared across every channel the grader
  opens. Never rebuild state per call or per connection. Implement the
  mandated "missing" behavior explicitly with `if key in ns:`-style branches —
  do not let proto3 defaults answer for you by accident. Proto3 defaults render
  as empty in debug text (`int 0`, `bool false`), which is correct wire data
  but looks like a bug when printed; compare parsed values, not reprs. For
  aggregate/multi-key/conditional ops, compute inside the lock and return one
  response per the instruction. If a condition must fail the call itself
  (e.g., a conditional update that does not apply), set
  `context.set_code(grpc.StatusCode.<CODE>)` and `context.set_details(...)`
  then return a default-constructed response — an unhandled exception
  otherwise surfaces as an UNKNOWN status with no details. Python ints are
  unbounded but protobuf int32/int64 **are** bounded — overflow beyond the
  declared type raises at serialization time; use `int32`/`int64` exactly as
  the instruction declares.
- **API structure (axis 1).** More methods = more servicer methods; the
  process is identical. `repeated` fields arrive/go out as Python lists of
  generated message objects; nested messages are nested generated classes;
  enums are generated enum classes accessed like
  `<mod>_pb2.<EnumName>.<VALUE>`; `optional` scalars have `HasField("x")`.
  If the service declares streaming RPCs, use `yield` per response message or
  iterate the request iterator — but for this family, unary handlers that
  `return` one message are the norm. If the proto declares more than one
  `service`, implement each servicer class and register ALL of them on the
  same server object (one `add_<Name>Servicer_to_server` call per service,
  same port) — tests may call any of them.
- **Concurrency / lifecycle (axis 3).** Always pass an explicit
  `ThreadPoolExecutor(max_workers≥16)`; do not rely on the default pool size.
  Guard all state access with one lock so concurrent bursts stay consistent.
  `server.start()` then `server.wait_for_termination()` keeps the process
  alive indefinitely — do not use a `time.sleep()` loop that could end.

Cross-check by introspection before launching: every RPC name in the service
must have a same-named method on your servicer class, otherwise the stub
answers UNIMPLEMENTED and tests fail.

Keep the server startup inside the `if __name__ == "__main__":` guard. The
grader may `import` your module to assert the mandated class name exists, and
an import-time `serve()` would block that import forever.

## Step 5 — kill stale servers, then launch detached so it survives your shell

The grader runs tests in a *different shell* after you finish. A foreground or
plain `&` child can die with your session.

**First, the stale-process trap (observed, important).** gRPC servers bind
with SO_REUSEPORT by default, so a *second* server can start on an
already-busy port without any error — the kernel then splits new connections
between the two listeners (measured ~50/50). A leftover server from an
earlier attempt hijacks roughly half of the grader's requests and fails you
even though your launch "succeeded". `add_insecure_port` returning the port
is NOT proof the port is exclusively yours. So: kill stale servers *before*
launching, and verify with multiple fresh connections afterwards (Step 6).

There is no `ps`/`pgrep`, so locate stale processes via /proc in **two
phases — list first, then kill only the pids you listed**. Match whole argv
tokens: `argv[0]` is the interpreter binary and one argument equals the
script file this task tells you to serve (use that task's script name, not a
hardcoded `server.py`; use the interpreter you actually launch with):
```python
import os
SCRIPT = 'server.py'          # the script path this task mandates
for pid in os.listdir('/proc'):
    if not pid.isdigit():
        continue
    try:
        with open(f'/proc/{pid}/cmdline', 'rb') as f:
            argv = f.read().split(b'\0')[:-1]
    except Exception:
        continue
    if argv and argv[0].endswith(b'python3') and \
       any(os.path.basename(a.decode(errors='ignore')) == SCRIPT for a in argv[1:]):
        print('candidate', pid, argv)      # PHASE 1: print only
```
Then kill exactly the printed pids: `os.kill(int(pid), signal.SIGKILL)` in a
`try/except ProcessLookupError`. The strict matcher cannot match the scanner
itself or its shell wrapper. **Never relax it to a bare substring search**
like `'server.py' in cmdline`: the heredoc that contains this very snippet
has `server.py` in its own command line, so a loose matcher lists (and would
kill) the scanning shell — observed both for me and in solver trajectories.
If a scan finds a process you did not start (different script name), list
with `SCRIPT` set to that name, review what it is, and only then kill; never
ship with a port answering from a process you cannot account for.

**Launch** with `setsid` so the process leaves your session, redirect all
streams, feed `/dev/null`:

```bash
cd /app && setsid nohup python3 server.py > /tmp/kv_server.log 2>&1 < /dev/null &
sleep 2; cat /tmp/kv_server.log
```
- Launch from the directory holding `server.py` and the generated modules:
  for a script, `sys.path[0]` is the **script's directory**, not the cwd, so a
  server elsewhere with a different cwd cannot import the pb2 modules
  (observed failure moving the same script to a different directory).
- Check the log for `Traceback` / `ModuleNotFoundError` before anything else.

## Step 6 — verify over the wire before finishing

Run a real client using your *generated* stubs (this is the same path the
grader uses). Cover every RPC, the missing-key/missing-namespace semantics,
and state persistence across fresh channels. The client must import the
generated modules, so either run inline from the artifact directory
(`cd /app && python3 - <<'EOF' ... EOF` — stdin scripts put the cwd on
`sys.path`) or save the whole check as `/tmp/smoke.py` and run it with
`PYTHONPATH=/app`. A script in `/tmp` without `PYTHONPATH` cannot import the
pb2 modules, because `sys.path[0]` is the *script's* directory, not the cwd
(observed). If you save a script, **create the file and execute it in the same
command** (a `cat > /tmp/smoke.py <<'EOF' ... EOF` heredoc followed on the
next line by `PYTHONPATH=/app python3 /tmp/smoke.py`), so every run happens
after the file exists.

```python
import grpc, <mod>_pb2, <mod>_pb2_grpc
PORT = 'localhost:<PORT>'

def new_stub():
    c = grpc.insecure_channel(PORT)
    grpc.channel_ready_future(c).result(timeout=10)    # readiness gate
    return c, <mod>_pb2_grpc.<ServiceName>Stub(c)

# Channel discipline (a solver crashed here): a stub dies with the channel it
# was built on — using it after `.close()` raises
# `ValueError: Cannot invoke RPC on closed channel!`. Keep ONE channel open
# for the whole sequential section and put its `.close()` as the LAST line of
# the script; close helper channels only once their stub is finished.
ch, stub = new_stub()
sentinel = 917_331_299                                # unique, unlikely value
# 1) on `stub`: exercise EVERY rpc and assert the instruction's semantics —
#    overwrite-on-write, missing-key/namespace defaults, isolation,
#    delete present+absent, aggregate/conditional rules. Make each assertion
#    write before it reads so the script stays re-runnable.
# 2) persistence across fresh channels + stale co-bound server detector:
<write sentinel via stub>
seen = set()
for _ in range(5):
    c, s = new_stub()
    seen.add(s.<ReadRpc>(<mod>_pb2.<ReadReq>(...)).<field>)
    c.close()                                         # this stub is done
assert seen == {sentinel}   # exactly ONE server process answered all channels

# 3) optional burst leg if the variant may serve concurrent traffic (axis 3):
from concurrent.futures import ThreadPoolExecutor, as_completed

def worker(t):
    c, s = new_stub()
    try:
        for i in range(20):
            v = t * 1000 + i
            assert s.<WriteRpc>(<mod>_pb2.<WriteReq>(key=f't{t}i{i}', value=v), timeout=10).<field> == v
            assert s.<ReadRpc>(<mod>_pb2.<ReadReq>(key=f't{t}i{i}'), timeout=10).<field> == v
    finally:
        c.close()                                     # this stub is done

errs = []
with ThreadPoolExecutor(max_workers=30) as ex:
    for fut in as_completed([ex.submit(worker, t) for t in range(30)]):
        try: fut.result()
        except Exception as e: errs.append(repr(e))
assert not errs, errs[:3]
# then assert the aggregate/count RPC equals the expected closed-form value
ch.close()                                            # LAST line — nothing uses `stub` after this
```

A deadlock, a 1-worker pool that serializes to timeouts, or lost updates from
a missing lock all fail the burst leg even when the sequential smoke passes.

If the smoke crashes with `ValueError: Cannot invoke RPC on closed channel!`,
it is a bug in this client script (a stub used after its channel closed), not
a server fault — fix the script, do not restart or debug the server over it
(observed). The sentinel put-then-fetch works because a stale co-bound server
has its own state and answers the fetch with a different (missing-key) value.

If the port is unreachable or `channel_ready_future` times out, check the
log, confirm the bound address/port matches the instruction, and confirm no
earlier process swallowed the port (Step 5 trap). A raw `socket.connect` only
proves something listens — even a stale or non-gRPC listener would pass it;
the gRPC sentinel check above is the only proof the endpoint speaks your
protocol and that it is the only server on the port.

Finally re-run the smoke check from a **separate command** to confirm the
process outlives the launching shell — every command line you issue runs in
its own shell, so issuing the smoke once more *after* the launch command is
already a fresh-shell test; for an explicit one, `bash -lc 'cd /app &&
PYTHONPATH=/app python3 /tmp/smoke.py'` (run this only AFTER the command
that created `/tmp/smoke.py` — a solver once copied such a one-liner verbatim
and ran it before the file existed; keep the create-then-run order explicit).
One further invocation suffices: if the detached server answers from a shell
other than the one that launched it, it will answer for the grader too.

Leave every artifact at the exact mandated path in the working directory so
the grader's imports resolve; keep helper scripts (smoke client) in `/tmp`,
not the artifact directory.

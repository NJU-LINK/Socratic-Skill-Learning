# SQLite WAL Recovery

## Problem Statement

A SQLite database operating in WAL mode consists of three files:

| File | Role |
|------|------|
| `main.db` | Base database (B-tree pages) |
| `main.db-wal` | Write-Ahead Log (pending frame updates) |
| `main.db-shm` | Shared-memory index (regenerated by SQLite) |

The base database is intact but shows only a subset of the data because the WAL
file has been **encoded or obfuscated**. The solver must decode the WAL so SQLite
can apply the pending frames, then extract **all** records into a JSON file.

## Critical Warnings

### ⚠ WAL Auto-Checkpoint Trap

**Never open the database with `sqlite3` before the WAL is repaired.** When
SQLite opens a WAL-mode database and finds an invalid WAL header, it silently
discards the WAL and may delete the file on connection close. This destroys the
encoded data permanently.

**Always** follow this order:
1. Back up all files (`cp main.db main.db.bak`, `cp main.db-wal main.db-wal.bak`)
2. Decode the WAL to a separate file
3. Write the decoded WAL back alongside a copy of the base DB
4. Open with SQLite to read/checkpoint
5. Extract data and close

### ⚠ WAL File Structure Reference

All multi-byte integers are **big-endian**. Every field below is exactly 4 bytes.

```
WAL header (32 bytes total):
Offset  Size  Field
------  ----  -----
0       4     Magic number (0x377F0682 = BE checksums, 0x377F0683 = LE checksums)
4       4     WAL format version (3007000 = 0x002DE218)
8       4     Database page size (must match DB header offset 16-17)
12      4     Checkpoint sequence number
16      4     Salt-1
20      4     Salt-2
24      4     Checksum-1 (over bytes 0-23)
28      4     Checksum-2

Frame header (24 bytes each, repeated for every frame):
Offset  Size  Field
------  ----  -----
0       4     Page number (1-indexed)
4       4     Commit record size (0 = non-commit, N = last frame of txn commits N pages)
8       4     Salt-1 (must equal WAL header Salt-1)
12      4     Salt-2 (must equal WAL header Salt-2)
16      4     Checksum-1
20      4     Checksum-2

Frame page data: page_size bytes immediately following each 24-byte frame header.
```

> **⚠ Common pitfall**: Salt and checksum are each stored as **two separate
> 4-byte fields**, not a single 8-byte value. Use `struct.unpack(">I", ...)`
> (4 bytes), NOT `struct.unpack(">Q", ...)` (8 bytes) for each individual
> salt and checksum field.

## Recovery Strategy

### Phase 1: Diagnose the Encoding

Read the first 32 bytes of the WAL file. Compare against the expected header:

```python
# Known-good values for cross-referencing
WAL_MAGIC_BE = bytes.fromhex("377f0682")
WAL_MAGIC_LE = bytes.fromhex("377f0683")
WAL_VERSION  = (3007000).to_bytes(4, "big")   # 00 2d e2 18
# Page size: read from DB header at offset 16-17 (big-endian uint16)
```

**Diagnostic procedure:**

1. **Read raw bytes** of the WAL header (first 32 bytes) and the DB page size.
2. **Check for base64**: if the file is ASCII and passes `base64.b64decode`, try
   decoding and re-checking the magic.
3. **Try single-byte XOR** with every candidate key (0–255). For each, check
   whether bytes 0-3 decode to a valid magic AND bytes 4-7 decode to 3007000
   AND bytes 8-11 decode to the expected page size. This is an extremely strong
   12-byte known-plaintext filter — a false positive is astronomically unlikely.
4. **Try bitwise NOT** (0xFF inversion) — equivalent to XOR with 0xFF.
5. **Try multi-byte XOR**: derive the key from the first 4/8 known plaintext
   bytes, then check if it repeats over the rest of the header.
6. **Try byte swapping** (16-bit or 32-bit endian swap) if the above fail.

> **Key insight**: The first 12 bytes of the WAL header provide 12 bytes of
> known plaintext (magic + version + page size). This is sufficient to
> brute-force any single-byte XOR in 256 attempts, or derive a multi-byte
> repeating key up to 12 bytes long.

**Quick diagnostic code** (paste directly into `task_shell`):

```python
import struct

with open("/app/main.db-wal", "rb") as f:
    raw = f.read()

# Read page size from DB header (offset 16-17, big-endian uint16)
with open("/app/main.db", "rb") as f:
    f.seek(16)
    expected_ps = int.from_bytes(f.read(2), "big")

# Known plaintext: magic + version + page_size (12 bytes)
known = bytes.fromhex("377f0682") + (3007000).to_bytes(4, "big") + expected_ps.to_bytes(4, "big")

# Brute-force single-byte XOR
for key in range(256):
    decoded_hdr = bytes([b ^ key for b in raw[:12]])
    if decoded_hdr == known:
        print(f"Found key: 0x{key:02x}")
        # Decode the full file
        decoded = bytes([b ^ key for b in raw])
        magic = struct.unpack(">I", decoded[0:4])[0]
        version = struct.unpack(">I", decoded[4:8])[0]
        ps = struct.unpack(">I", decoded[8:12])[0]
        salt1 = struct.unpack(">I", decoded[16:20])[0]  # 4 bytes, NOT 8
        salt2 = struct.unpack(">I", decoded[20:24])[0]  # 4 bytes, NOT 8
        print(f"  magic=0x{magic:08x} version={version} ps={ps}")
        print(f"  salt1=0x{salt1:08x} salt2=0x{salt2:08x}")

        # Verify frame salts
        frame_size = 24 + ps
        for i in range((len(decoded) - 32) // frame_size):
            off = 32 + i * frame_size
            f_s1 = struct.unpack(">I", decoded[off+8:off+12])[0]
            f_s2 = struct.unpack(">I", decoded[off+12:off+16])[0]
            ok = f_s1 == salt1 and f_s2 == salt2
            pg = struct.unpack(">I", decoded[off:off+4])[0]
            cm = struct.unpack(">I", decoded[off+4:off+8])[0]
            print(f"  Frame {i}: page={pg} commit={cm} salt_ok={ok}")
        break
```

### Phase 2: Validate the Decoded WAL

After decoding, verify structural invariants **before** handing to SQLite:

1. **Magic**: must be `0x377F0682` or `0x377F0683`
2. **Version**: must be `3007000` (0x002DE218)
3. **Page size**: must match the base database's page size
4. **Salt consistency**: WAL header `Salt-1` (bytes 16-19) and `Salt-2` (bytes
   20-23) must each match the corresponding 4-byte fields in every frame header
   (bytes 8-11 and 12-15). If salts differ, the decoding is wrong.
5. **Frame count**: `(file_size - 32) / (24 + page_size)` should be a positive
   integer with zero remainder.
6. **Page numbers**: every frame's page number should be in `[1, total_db_pages]`
   or one beyond (for new pages).

If validation fails, go back to Phase 1 and try the next encoding candidate.

### Phase 3: Mount and Extract

```python
import struct, shutil, sqlite3, json, tempfile, os

# --- decoded_wal_bytes must already contain the decoded WAL binary ---
# --- (from the diagnostic step above)                             ---

# Read page size from the DB header (raw bytes, NOT via sqlite3)
with open("/app/main.db", "rb") as f:
    f.seek(16)
    page_size = int.from_bytes(f.read(2), "big")
if page_size == 1:
    page_size = 65536  # SQLite special-cases 1 → 65536

tmpdir = tempfile.mkdtemp()
tmp_db  = os.path.join(tmpdir, "main.db")
tmp_wal = tmp_db + "-wal"

def extract_all(conn_cursor):
    """Extract all records from all tables via the given cursor."""
    records = []
    conn_cursor.execute("SELECT name FROM sqlite_master WHERE type='table'")
    tables = [r[0] for r in conn_cursor.fetchall()]
    for table in tables:
        conn_cursor.execute(f"PRAGMA table_info({table})")
        cols = [r[1] for r in conn_cursor.fetchall()]
        conn_cursor.execute(f"SELECT * FROM {table}")
        for row in conn_cursor.fetchall():
            records.append(dict(zip(cols, row)))
    return records

# Step A: Count base-DB records (copy DB WITHOUT WAL to avoid triggering
#         SQLite's WAL parser on the still-encoded original)
shutil.copy2("/app/main.db", tmp_db)
base_conn = sqlite3.connect(tmp_db)  # no -wal file here, safe
base_records_count = 0
bc = base_conn.cursor()
for t in bc.execute("SELECT name FROM sqlite_master WHERE type='table'"):
    base_records_count += bc.execute(f"SELECT COUNT(*) FROM {t[0]}").fetchone()[0]
base_conn.close()
print(f"Base DB has {base_records_count} records")

# Step B: Write decoded WAL and try to let SQLite apply it
with open(tmp_wal, "wb") as f:
    f.write(decoded_wal_bytes)

conn = sqlite3.connect(tmp_db)
conn.execute("PRAGMA wal_autocheckpoint=0")
cur = conn.cursor()
records = extract_all(cur)

# Step C: If WAL was NOT applied, manually write frames into the DB
if len(records) <= base_records_count:
    print(f"WAL not applied ({len(records)} records). Using manual fallback.")
    conn.close()
    os.remove(tmp_wal)                # remove stale WAL
    shutil.copy2("/app/main.db", tmp_db)  # reset DB to base
    frame_size = 24 + page_size
    with open(tmp_db, "r+b") as f:
        for i in range((len(decoded_wal_bytes) - 32) // frame_size):
            off = 32 + i * frame_size
            pg = struct.unpack(">I", decoded_wal_bytes[off:off+4])[0]
            page_data = decoded_wal_bytes[off+24:off+24+page_size]
            if pg >= 1:
                f.seek((pg - 1) * page_size)
                f.write(page_data)
        # Bump file-change counter at DB offset 24-27
        f.seek(24)
        cc = int.from_bytes(f.read(4), "big")
        f.seek(24)
        f.write((cc + 1).to_bytes(4, "big"))
    conn = sqlite3.connect(tmp_db)
    conn.execute("PRAGMA wal_autocheckpoint=0")
    cur = conn.cursor()
    records = extract_all(cur)

conn.close()

# Sort by primary key / first integer column
records.sort(key=lambda r: r.get("id", 0))

with open("/app/recovered.json", "w") as f:
    json.dump(records, f, indent=2)

print(f"Recovered {len(records)} records → /app/recovered.json")
```

**Important notes:**
- The `-shm` file does not need to exist; SQLite will recreate it.
- **Always** set `PRAGMA wal_autocheckpoint=0` before reading to prevent
  premature checkpointing.
- Read all data **before** closing the connection. Once closed, the WAL is gone.
- **Checksum fallback** (included in the code above): If SQLite rejects the
  decoded WAL due to checksum mismatch, the record count stays at the base-DB
  level. The code above detects this and falls back to directly writing each
  frame's page data into the database file at offset `(page_number - 1) *
  page_size`, then reopens and extracts.

### Phase 4: Output

Write the records as a JSON array of objects, sorted by the primary key (or
first column if no column named `id` exists). Ensure:
- All recovered records are present (base DB rows + WAL-applied rows).
- Column names match the schema exactly.
- Numeric values are numbers, not strings.
- The file is at the path specified by the task (typically `/app/recovered.json`).

## Handling Variation Axes

### wal_encoding_or_obfuscation

| Encoding | Detection Signal | Reversal |
|----------|-----------------|----------|
| Single-byte XOR | 12-byte known-plaintext match | XOR entire file with key byte |
| Multi-byte XOR (≤12) | Repeating key derived from known header bytes | XOR with repeating key |
| Base64 wrapper | File is ASCII, decodes to binary with valid magic | `base64.b64decode` |
| Bitwise NOT / inversion | XOR with 0xFF passes header check | Invert all bits |
| Byte swapping | Swapped bytes pass header check | Swap back |
| Damaged header fields | Partial match, some fields correct | Patch specific fields |
| No encoding (intact WAL) | Magic already valid | No transformation needed |

### wal_and_base_database_integrity

- **Base DB usable, WAL encoded**: Most common case. Decode WAL, mount with base.
- **Base DB missing**: Extract pages from WAL directly, reconstruct from schema
  embedded in page 1 (sqlite_master table).
- **Corrupted frame page numbers**: Use B-tree structure to identify which pages
  belong to which tables.
- **Partial frames**: Discard incomplete trailing frame if `file_size % frame_size != 0`.
- **Multiple WAL files**: Process each separately, merge results by primary key.

### recovery_depth

- **Shallow**: Decoded WAL is valid → SQLite auto-applies on open. Just open and read.
- **Medium (checksum mismatch)**: WAL structure is valid (magic, version, page
  size, salts all correct) but SQLite rejects it due to checksum mismatch.
  This is very common: obfuscation is typically applied to the *entire* WAL file
  after checksums were computed, so decoded checksums don't match the standard
  algorithm. Solution: manually apply frame page data directly to the database
  file at offset `(page_number - 1) * page_size`, increment the file-change
  counter at DB offset 24-27, then reopen and extract. The Phase 3 code above
  includes this fallback automatically.
- **Deep**: WAL frames contain valid page data but headers are damaged → Extract
  raw page bytes, build a fresh database, insert pages using SQLite's file API.

### schema_and_update_topology

- Discover schema dynamically via `sqlite_master` and `PRAGMA table_info`.
- Handle multiple tables by iterating over all tables.
- Preserve referential integrity by sorting within each table by primary key.
- Handle varying column types (INTEGER, TEXT, REAL, BLOB, NULL).

## Automated Recovery Script

A helper script is provided at `scripts/recover_wal.py`:

```bash
python3 scripts/recover_wal.py \
    --db /app/main.db \
    --wal /app/main.db-wal \
    --output /app/recovered.json
```

The script performs all four phases automatically:
1. Backs up original files
2. Auto-detects encoding by trying candidates in priority order
3. Validates decoded WAL structure
4. Mounts with the base DB and extracts all records to sorted JSON

## Verification Checklist

After recovery, verify:

- [ ] `/app/recovered.json` exists and contains valid JSON
- [ ] Record count matches the expected total (base + WAL records)
- [ ] Records are sorted by the primary key
- [ ] All columns present with correct types
- [ ] No duplicate primary keys
- [ ] Original files backed up (`.bak` files exist)
